# NewsFlow 新闻流自动化处理指令

这是一个自动化流程，用于从配置的网站提取最新内容（包括新闻文章、技术博客、GitHub 热门项目等），生成总结并发送邮件。

## 执行步骤

### 第一步：创建输出目录并初始化

1. **创建日期文件夹**：
   - 调用 MCP 工具 `create_date_folder`（不传日期参数，使用今天）
   - 确保输出目录存在

2. **初始化有价值链接 JSON 文件**：
   - `create_date_folder` 会在日期文件夹中自动创建 `valuable_links.json` 文件
   - 该文件用于记录从各网站收集到的有价值内容链接，供后续步骤使用

### 第二步：读取配置文件

读取项目根目录下的 `config.yaml` 文件，获取以下信息：
- `websites`: 网站列表（包含 `name`, `url`, `enabled`）
- `email`: 邮件配置（包含 `recipient_emails`）
- `settings`: 其他设置（如 `max_articles_per_site`）

**注意**：只处理 `enabled: true` 的网站。

### 第三步：提取所有网站的内容链接

对每个启用的网站执行以下操作：

1. 调用 MCP 工具 `extract_links_from_url`，传入网站的 `url`
2. 获取返回的 `links` 数组（包含该网站提取到的所有链接）
3. 分析这些链接，识别出有价值的内容链接：
   - **新闻文章**：技术新闻、行业动态、产品发布等
   - **技术博客**：技术教程、经验分享、技术深度分析等
   - **GitHub 热门项目**：趋势仓库、优秀的开源项目、有特色的项目等
   - **其他有价值内容**：研究报告、产品介绍、工具推荐等
   - 查看链接文本和URL模式
   - 过滤掉导航链接、登录页、用户协议、关于我们等无关链接
   - 保留看起来是有价值内容的链接（包括文章、项目、资源等）

4. **重要：每个网站至少提取5篇有价值内容**
   - **目标**：每个启用的网站必须至少识别出5篇有价值的内容
   - **策略**：
     * 如果首次识别出的有价值链接少于5篇，需要继续分析更多链接
     * 可以放宽筛选标准，但必须确保内容确实有价值
     * 如果该网站确实没有足够的有价值内容，记录实际情况，但尽量达到5篇
   - **优先级**：优先选择质量高、价值大的内容，但数量要求优先于质量筛选
   - **记录**：记录每个网站实际提取到的有价值内容数量

5. 如果配置中有 `max_articles_per_site` 限制，则：
   - 如果提取到的有价值内容数量 >= `max_articles_per_site`，则保留前N个
   - 如果提取到的有价值内容数量 < `max_articles_per_site`，但 >= 5，则保留所有
   - 如果提取到的有价值内容数量 < 5，则继续尝试提取更多，直到达到5篇或没有更多内容

6. **收集并写入 JSON**：
   - 每收集完一个网站的有价值链接后，调用 MCP 工具 `append_valuable_links_to_json`，传入：
     - `date`: 今天的日期（YYYY-MM-DD格式）
     - `site_name`: 来源网站名称（如 "Hacker News"、"TLDR"、"GitHub Trending"）
     - `links`: 该网站识别出的有价值链接数组，每项包含 `url` 和 `text`
   - 该工具会将链接追加到日期文件夹中的 `valuable_links.json` 文件
   - 收集完所有网站后，该 JSON 文件包含所有来源的有价值链接

7. 收集所有网站的内容链接到一个总列表中（用于后续处理）

**重要提示**：
- 使用 AI 能力智能识别有价值的内容链接，而不是简单的 URL 模式匹配
- 对于不同类型的网站，识别不同类型的内容：
  - **新闻网站**：识别新闻文章、深度报道等
  - **技术博客**：识别技术文章、教程、经验分享等
  - **GitHub Trending**：识别热门仓库、优秀的开源项目等
  - **其他网站**：根据网站特点识别有价值的内容
- 每个链接都要判断其是否为有价值的内容（文章、项目、资源等）
- 记录每个链接的来源网站和内容类型（方便后续追踪）
- **数量要求**：每个网站至少5篇有价值内容，这是硬性要求

### 第四步：处理每个内容链接

对汇总后的每个内容链接执行以下操作（无论是新闻文章、技术博客还是 GitHub 项目）：

1. **读取内容（必须步骤，不能跳过）**：
   
   **⚠️ 重要要求**：在生成总结之前，必须先访问链接获取实际内容，**绝对不能基于URL或链接文本进行猜测**。必须读取到真实的内容才能生成总结。
   
   **对于文章类内容**（新闻、博客等）：
   - **必须步骤1**：使用 MCP 工具 `fetch_html_from_url` 访问该文章链接，获取完整的HTML内容
   - **必须步骤2**：从HTML中提取以下实际内容：
     * **文章标题**：从 `<title>` 标签或页面中的 `<h1>`、`<h2>` 等标题标签提取
     * **文章正文**：从 `<article>`、`<main>`、或包含文章内容的 `<div>` 标签中提取
     * **发布时间**：如果页面中有时间信息，提取发布时间
     * **作者信息**：如果页面中有作者信息，提取作者
     * **文章摘要/描述**：如果页面中有meta description或摘要，提取摘要
   - **验证要求**：确保提取到的正文内容长度合理（至少200字），如果内容过短或无法提取，记录错误并跳过
   - **禁止行为**：不能仅根据URL猜测文章内容，不能仅根据链接文本生成总结
   
   **对于 GitHub 项目**：
   - **必须步骤1**：使用 MCP 工具 `fetch_html_from_url` 访问该GitHub仓库链接，获取完整的HTML内容
   - **必须步骤2**：从HTML中提取以下实际内容：
     * **项目名称**：从页面标题或仓库名称区域提取
     * **项目描述**：从仓库描述区域提取
     * **README内容**：从README.md渲染后的内容中提取（这是最重要的）
     * **Star数、Fork数**：从页面统计信息中提取
     * **编程语言**：从语言统计信息中提取
     * **主要功能**：从README中的功能列表、特性说明等部分提取
     * **安装和使用方法**：从README中的安装、使用说明部分提取
   - **验证要求**：确保提取到README内容，如果README为空或无法访问，记录错误并跳过
   - **禁止行为**：不能仅根据项目名称或URL猜测项目功能，必须读取README等实际内容
   
   **通用要求**：
   - 如果访问失败（网络错误、404、403等），记录具体错误信息并跳过该链接
   - 如果提取到的内容为空或过短，记录警告并跳过该链接
   - 如果内容提取成功，将提取到的实际内容保存下来，用于后续生成总结
   - **关键原则**：总结必须基于实际读取到的内容，不能有任何猜测或假设

2. **生成AI总结（基于实际读取的内容）**：
   
   **⚠️ 重要要求**：总结必须严格基于步骤2中实际读取到的内容生成，不能添加任何未在原文中出现的信息。
   
   - **对于文章类内容**：基于步骤2中实际提取到的文章标题和正文内容生成总结
     - 如果正文内容不完整，只能基于已读取的部分生成总结，不能猜测未读取的部分
     - 如果标题缺失，使用URL或链接文本作为标题，但要标注"标题缺失"
   
   - **对于 GitHub 项目**：基于步骤2中实际提取到的项目描述、README内容、统计信息等生成总结
     - 如果README内容不完整，只能基于已读取的部分生成总结
     - 如果某些信息（如Star数、语言）无法提取，可以在总结中说明"信息未获取"
   
   **a. 简短摘要（summary）**：
   - **对于文章类**：生成约200字的中文总结，采用轻松、口语化的表达方式
     - 总结应该包含：文章核心观点、关键信息、主要结论
   - **对于 GitHub 项目**：生成约200字的中文总结，同样采用轻松、口语化的表达方式
     - 总结应该包含：项目用途、主要功能、技术栈、适用场景
     - 语气要自然放松，像介绍一个有趣的工具或项目给朋友一样
   - 语气要自然放松，像朋友聊天一样娓娓道来 🗣️
   - 在合适的位置适当添加表情符号，让总结更生动有趣 😊（比如：👍 表示赞同、💡 表示观点、🚀 表示创新/突破、⚡ 表示快速/重要、⭐ 表示热门项目、💻 表示技术工具等）
   - 避免过于正式和生硬的表达，让读者阅读起来更轻松愉悦 ✨
   
   **b. 详细概括（detailed_summary）**：
   - **对于文章类**：生成详细的内容概括（500-800字），包含以下结构化的部分：
     * **背景信息**：简要介绍文章主题和背景
     * **核心要点**：列出2-5个主要观点（用编号列表或段落形式）
     * **关键信息**：重要的数据、事实、发现或具体案例
     * **影响分析**：这个内容可能带来的影响、意义或启示
     * **结论**：文章的核心结论或主要观点总结
   - **对于 GitHub 项目**：生成详细的项目概括（500-800字），包含以下结构化的部分：
     * **项目背景**：项目解决的问题、应用场景、目标用户
     * **核心功能**：项目的主要功能、特性、技术亮点
     * **技术栈**：使用的编程语言、框架、工具等
     * **项目亮点**：项目的独特之处、创新点、优势
     * **使用建议**：适用场景、使用建议、学习价值
   - 保持轻松、口语化的风格，但内容要更加详细和全面
   - 可以使用表情符号增强可读性，但不要过度使用
   - 确保详细概括是对内容的深入分析，而不仅仅是简短摘要的扩展版本

3. **保存为Markdown文件**：
   - 调用 MCP 工具 `save_markdown_file`，传入以下参数：
     - `title`: 内容标题（格式：中文标题（英文原标题/项目名），用于文件名，会自动进行安全处理）
     - `original_title`: 内容标题（格式：中文标题（英文原标题/项目名），用于Markdown中的"原名"字段）
     - `summary`: AI生成的200字简短摘要
     - `detailed_summary`: AI生成的500-800字详细概括（**必须生成，不能为空**）
     - `url`: 内容原始URL（文章链接或 GitHub 仓库链接）
     - `date`: 今天的日期（YYYY-MM-DD格式，可选）
     - `skip_if_exists`: `true`（如果内容已分析过则跳过）

4. **错误处理**：
   - 如果某个链接处理失败，记录错误信息但继续处理其他链接
   - 不要因为一个链接失败而中断整个流程

### 第五步：发送邮件

当所有链接都处理完成后：

1. 调用 MCP 工具 `send_email_from_date_folder`，传入以下参数：
   - `date`: 今天的日期（YYYY-MM-DD格式）
   - `recipient_email`: 从 `config.yaml` 的 `email.recipient_emails` 读取（支持多个收件人）
   - `subject`: 可选，默认会使用配置中的 `default_subject_prefix`

2. 该工具会自动：
   - 读取今天日期文件夹中的所有Markdown文件
   - 解析每篇文章的信息（原名、AI总结、详细概括、原文链接）
   - 生成格式化的HTML邮件
   - 发送到所有指定的收件人

3. **邮件内容**：
   - 包含所有成功处理的内容（文章、项目等）
   - 每个内容显示：
     * **原标题/项目名**：内容的原始标题或项目名称
     * **简短摘要（AI总结）**：约200字的中文总结，轻松口语化的表达方式
     * **详细概括**：500-800字的详细内容概括（对于文章包含背景信息、核心要点、关键信息、影响分析和结论；对于项目包含项目背景、核心功能、技术栈、项目亮点和使用建议），以折叠形式展示，点击"查看详细概括"可展开
     * **原文链接**：内容原始URL（文章链接或 GitHub 仓库链接）
   - 美观的HTML格式，详细概括默认折叠，方便快速浏览和深入阅读

### 第六步：总结报告

处理完成后，给出一个总结报告：
- 共处理了多少个网站
- 总共提取了多少个内容链接（包括文章、项目等）
- 成功处理了多少篇内容（按类型分类：文章数、项目数等）
- 失败了多少篇内容（如果有）
- 邮件是否发送成功
- 如果有失败的情况，列出失败原因

## 重要注意事项

1. **数量要求**：每个启用的网站必须至少提取5篇有价值的内容，这是硬性要求
   - 如果某个网站无法达到5篇，需要记录原因（如网站内容不足、链接提取失败等）
   - 优先保证数量，在数量达标的前提下再考虑质量筛选

2. **内容真实性要求**：**绝对不能猜测内容**
   - 必须使用 `fetch_html_from_url` 工具访问每个链接获取实际HTML内容
   - 必须从HTML中解析出标题、正文、README等实际内容
   - 总结必须基于实际读取到的内容生成，不能添加未在原文中出现的信息
   - 如果无法读取到实际内容，必须跳过该链接，不能基于猜测生成总结

3. **并发控制**：可以并行处理多个链接以提高效率，但要注意不要超过系统资源限制

4. **去重处理**：如果多个网站提取到了相同的链接，需要去重，只处理一次

5. **错误恢复**：如果中途出现错误，应该继续处理其他链接，不要中断整个流程

6. **日志记录**：记录关键步骤的执行情况，特别是：
   - 每个网站提取到的有价值内容数量
   - 内容读取成功/失败的情况
   - 内容提取失败的原因

7. **时间格式**：日期使用 `YYYY-MM-DD` 格式（如 `2025-01-15`）

8. **内容验证**：
   - 文章正文长度至少200字，否则视为无效内容
   - GitHub项目必须能读取到README内容，否则视为无效内容
   - 如果内容提取不完整，在总结中标注"内容不完整"

## 技术实现要点

1. **配置文件读取**：直接读取 `config.yaml` 文件（使用 `read_file` 工具）

2. **输出目录**：使用 MCP 工具 `create_date_folder` 创建日期文件夹并初始化 `valuable_links.json`

3. **链接提取**：使用 MCP 工具 `extract_links_from_url` 从网站首页提取所有链接

4. **链接记录**：每收集完一个网站后，使用 MCP 工具 `append_valuable_links_to_json` 将有价值链接写入 JSON

5. **内容获取（关键步骤）**：
   - **必须使用** MCP 工具 `fetch_html_from_url` 访问每个内容链接，获取实际HTML内容
   - 该工具会返回完整的HTML页面源码，需要从中解析出：
     * 文章标题（从 `<title>` 或页面标题标签提取）
     * 文章正文（从 `<article>`、`<main>` 或主要内容区域提取）
     * GitHub项目的README内容（从渲染后的README区域提取）
     * 其他相关信息（作者、时间、统计信息等）
   - **禁止**：不能仅根据URL、链接文本或页面标题猜测内容，必须读取完整内容
   - **验证**：确保提取到的内容长度合理，如果内容过短或无法提取，跳过该链接

6. **内容解析**：
   - 使用HTML解析技术（BeautifulSoup或类似工具）从HTML中提取结构化内容
   - 对于文章：提取标题、正文段落、作者、时间等
   - 对于GitHub项目：提取项目名、描述、README、统计信息等

7. **文件保存**：使用 MCP 工具 `save_markdown_file` 保存Markdown文件

8. **邮件发送**：使用 MCP 工具 `send_email_from_date_folder` 发送邮件摘要

## 执行此指令

当用户说"执行newflow"或类似指令时，按照上述步骤顺序执行整个流程。
